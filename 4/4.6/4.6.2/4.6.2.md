# 4.6.2. Modelo de Coordinación

Esta categoría reúne las decisiones sobre cómo interactúan los elementos del sistema: qué mecanismo de comunicación usa cada interacción (síncrono o asíncrono) y qué propiedades debe tener (oportunidad, completitud y consistencia).

## Decisión global

#### ADR-GLO-03 · Comunicación entre microservicios

**Título**:
- REST síncrono para todo vs eventos de dominio por mensajería para todo vs modelo híbrido (eventos + REST solo para consultas inmediatas)

**Contexto**:
- Con microservicios (ADR-GLO-01), los cinco módulos deben intercambiar información ([2.1.6](../../../2/2.1/2.1.6/2.1.6.md)). Hay dos tipos de interacción: **consultas que el usuario espera en el momento** (el checkout necesita el precio y stock vigentes del Catálogo, ESC-CAT-07, y la cotización de Logística, ESC-PED-01) y **hechos de negocio que otros módulos deben enterarse sin perderse ni duplicarse** (`PagoConfirmado`, `SubpedidoCreado`, `EntregaConfirmada`, `DisputaResuelta`, `VendedorSuspendido`). Un evento perdido o duplicado tiene costo real: un pedido confirmado dos veces (ESC-PED-07) o un periodo de reclamo iniciado dos veces (ESC-PAG-10). El módulo de Vendedores ya eligió RabbitMQ como broker (ADR-TAC-VEN-01) y el patrón outbox (ADR-VEN-03).

**Alternativas**:
1. **REST síncrono para todas las interacciones**
   - Cada módulo invoca la API del otro cuando necesita algo; es simple de entender y depurar.
   - Si el destinatario está caído, la operación falla o hay que reintentar a mano; la disponibilidad de cada módulo queda atada a la de los demás.
2. **Eventos de dominio por mensajería para todas las interacciones**
   - Desacopla emisor y receptor en el tiempo; el broker retiene los mensajes.
   - No sirve para consultas que el usuario espera en el momento: obtener el precio vigente por un evento obliga a correlacionar respuestas asíncronas dentro del checkout.
3. **Modelo híbrido: eventos de dominio para los hechos de negocio y REST síncrono solo para consultas inmediatas**
   - Cada interacción usa el mecanismo que corresponde a su naturaleza.
   - Hay que operar un broker y mantener dos tipos de contrato (eventos y APIs).

**Criterios de Elección**:
- No perder ni duplicar hechos de negocio (0 pedidos duplicados, 100% de eventos con efecto único: ESC-PED-07, ESC-PAG-10).
- Que la caída de un módulo no bloquee a otro (ESC-VEN-07: resolver una disputa no debe fallar si Pagos está caído).
- Tiempos de respuesta del checkout (p95 de 300 ms para precio y stock, ESC-CAT-07).
- Coherencia con lo ya decidido en el módulo de Vendedores (ADR-VEN-03, ADR-TAC-VEN-01).

**Decisión**:
- Se elige la alternativa 3: **modelo híbrido**.
  - **Eventos de dominio** sobre RabbitMQ (servicio gestionado Amazon MQ for RabbitMQ): un exchange de tipo *topic* `qhatu.eventos`, routing key `<Evento>.v<versión>` (p. ej. `EntregaConfirmada.v1`), una cola durable por consumidor y una cola de mensajes fallidos por cola.
  - **Entrega confiable**: cada productor guarda el evento en la misma transacción que el cambio que lo origina (outbox) y un publicador lo envía al broker; cada consumidor registra los identificadores de evento ya procesados para ignorar duplicados.
  - **REST/JSON síncrono** versionado (`/v1`) a través de la red interna, solo para las operaciones cuyo resultado el usuario espera dentro de la misma interacción: precio y stock vigentes (Catálogo), cotización de envío (Logística) e inicio del cobro en el checkout (Pagos, con `Idempotency-Key` para no cobrar dos veces). El resultado final del cobro llega después por eventos (`PagoConfirmado` o `PagoRechazado`).

**Sustento**:
- Los hechos de negocio viajan por eventos, así que el emisor no depende de que el receptor esté disponible: el broker retiene el mensaje y el outbox garantiza que ninguna decisión quede sin notificar. Los consumidores idempotentes cubren la duplicación que implica la entrega al-menos-una-vez, que es justo lo que piden ESC-PED-07 y ESC-PAG-10. Las dos consultas síncronas son las únicas donde el usuario espera la respuesta en la misma pantalla; para ellas, los propios módulos definen respaldos ante falla (p. ej. la tarifa de respaldo de ESC-PED-01). Se generaliza a todo el sistema el broker y el patrón ya elegidos por Vendedores, sin sumar otra tecnología.

### Contratos de integración entre módulos

| Evento / API | Tipo | Publica / expone | Consume | Requisitos |
|---|---|---|---|---|
| API de precio y stock (`/v1`) | REST síncrono | Catálogo | Pedidos | RF-CAT-10, RF-PED-04 |
| API de cotización de envío (`/v1`) | REST síncrono | Logística | Pedidos | RF-LOG-01, RF-PED-03 |
| API de cobros (`POST /v1/cobros`, con Idempotency-Key) | REST síncrono | Pagos | Pedidos | RF-PED-05, RF-PAG-01 |
| `PagoConfirmado` | Evento | Pagos | Pedidos, Catálogo | RF-PAG-02, RF-PED-06, RF-CAT-11 |
| `PagoRechazado` | Evento | Pagos | Pedidos | RF-PAG-02, RF-PAG-03, RF-PED-07 |
| `SubpedidoCreado` | Evento | Pedidos | Logística, Vendedor | RF-PED-06, RF-LOG-03 |
| `EntregaConfirmada` | Evento | Logística | Pagos, Vendedores, Pedidos | RF-LOG-09, RF-PAG-04, RF-VEN-05, RF-PED-07 |
| `DisputaResuelta` | Evento | Vendedores | Pagos | RF-VEN-09, RF-PAG-06 |
| `VendedorSuspendido` | Evento | Vendedores | Catálogo | RF-VEN-10, RF-CAT-12 |
| `PedidoCancelado` | Evento | Pedidos | Pagos, Catálogo, Logística | RF-PED-10, RF-PAG-06, RF-CAT-11, RF-LOG-10 |
| `CuentaBancariaCambiada` | Evento | Pagos | Pedidos (`svc-notificaciones`) | RF-PAG-08 |

```json
}
```
