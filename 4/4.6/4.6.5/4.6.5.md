# 4.6.5. Elección de Tecnología

Esta sección consolida el stack tecnológico del sistema. Las decisiones globales aplican a todos los módulos; las tecnologías propias de cada módulo se documentan en su sección 4.N o 5.N y se resumen al final.

## Decisiones globales

#### ADR-GLO-05 · Proveedor de nube pública

**Título**:
- Amazon Web Services vs Google Cloud vs Microsoft Azure

**Contexto**:
- RES-09 obliga a desplegar en una nube pública con presupuesto limitado, usando servicios gestionados y escalamiento solo en campaña. Las decisiones ya tomadas requieren servicios gestionados equivalentes para un broker RabbitMQ (ADR-TAC-VEN-01), PostgreSQL con réplica en otra zona (ADR-VEN-04, ADR-TAC-VEN-02), contenedores con autoescalado (ADR-GLO-06), un proveedor de identidad (ADR-GLO-02) y un motor de búsqueda (Catálogo, [4.3](../../4.3/4.3.md)). La operación es en Perú (RES-07) y los datos personales deben protegerse según la Ley 29733 (RES-01).

**Alternativas**:
1. **Amazon Web Services (AWS)**
   - Ofrece todos los servicios necesarios como gestionados: Amazon MQ for RabbitMQ, RDS for PostgreSQL Multi-AZ, ECS Fargate, Cognito, OpenSearch Service, S3 y KMS. Región más cercana: São Paulo (sa-east-1). Programa de créditos para startups.
   - Su región sudamericana es más cara que las de Estados Unidos.
2. **Google Cloud**
   - Cloud Run, Cloud SQL y un buen modelo de precios; región en Santiago de Chile.
   - No tiene un RabbitMQ gestionado propio: habría que reemplazarlo por Pub/Sub (otra semántica, contra ADR-TAC-VEN-01) o autogestionarlo.
3. **Microsoft Azure**
   - Container Apps, Azure Database for PostgreSQL y Entra ID; región en Brasil.
   - Tampoco ofrece RabbitMQ gestionado (su equivalente es Service Bus) y el equipo no tiene experiencia con la plataforma.

**Criterios de Elección**:
- Disponibilidad como servicio gestionado de cada pieza ya decidida (sobre todo RabbitMQ y PostgreSQL con réplica).
- Latencia hacia Lima.
- Costo y acceso a créditos para el MVP y el piloto ([1.1](../../../1/1.1/1.1.md)).
- Documentación y conocimiento disponible para el equipo.

**Decisión**:
- Se elige **AWS**, región **sa-east-1 (São Paulo)**, desplegando en **2 zonas de disponibilidad**.

**Sustento**:
- Es la única de las tres que ofrece como servicio gestionado todas las piezas ya decididas sin reemplazar el broker, lo que mantiene ADR-TAC-VEN-01 y evita operar RabbitMQ por cuenta propia. En latencia, la región de Google Cloud en Santiago está algo más cerca de Lima, pero la diferencia es de decenas de milisegundos y queda dentro de los presupuestos de los escenarios (p. ej. p95 de 1 s en la búsqueda, ESC-CAT-03); la región de São Paulo permite además repartir cada servicio en 2 zonas para los escenarios de disponibilidad. El sobrecosto de la región se compensa con el escalamiento solo en campaña (RES-09) y con los créditos para startups previstos en el financiamiento.

#### ADR-GLO-07 · Lenguaje y framework del backend de todos los microservicios

**Título**:
- Node.js con TypeScript y Express vs Java con Spring Boot vs Python con FastAPI (decisión para todo el sistema)

**Contexto**:
- Con cinco microservicios a cargo de cinco personas (RES-10), usar un solo stack facilita las revisiones cruzadas y el mantenimiento cuando un integrante debe tocar el servicio de otro. El módulo de Vendedores ya eligió Node.js con TypeScript y Express (ADR-VEN-06). Según las presentaciones (0.1), el equipo conoce Express (Almeyda, Gonzales, Luna), Spring Boot / Java (Santin, Luna) y Python / FastAPI (Luna, Sevillano). La carga de los servicios es mayormente de entrada/salida: consultas a la base de datos, llamadas a terceros y publicación y consumo de eventos.

**Alternativas**:
1. **Node.js con TypeScript y Express**
   - E/S no bloqueante, adecuada para cargas dominadas por consultas y llamadas externas; tipos estáticos para los contratos de eventos y APIs.
   - Es el stack que más integrantes conocen y el mismo lenguaje que el frontend (ADR-GLO-08).
2. **Java con Spring Boot**
   - Ecosistema maduro y tipado estático; lo conocen Santin y Luna.
   - Mayor consumo de memoria por contenedor (más costo en Fargate) y lo conocen menos integrantes.
3. **Python con FastAPI**
   - Desarrollo rápido; lo conocen Luna y Sevillano.
   - Tipado opcional y lo conocen menos integrantes.

**Criterios de Elección**:
- Cantidad de integrantes que dominan la tecnología (revisión cruzada y mantenimiento).
- Manejo de E/S concurrente en campaña.
- Contratos de eventos y APIs verificables por tipos.
- Consumo de recursos por contenedor (RES-09).
- Coherencia con ADR-VEN-06.

**Decisión**:
- Se elige **Node.js (versión LTS) con TypeScript y Express** como stack único de backend para todos los microservicios.

**Sustento**:
- Tres de los cinco integrantes ya conocen Express y TypeScript tiene una curva corta desde JavaScript, así que cualquier integrante puede revisar o mantener el servicio de otro. Compartir lenguaje con el frontend reduce la cantidad de tecnologías del equipo, y los tipos permiten validar los contratos de [4.6.2](../4.6.2/4.6.2.md) en tiempo de compilación. Los contenedores de Node consumen menos memoria que los de la JVM, lo que reduce el costo base en Fargate. Esta decisión ratifica ADR-VEN-06 a nivel de sistema.

#### ADR-GLO-08 · Tecnología del frontend

**Título**:
- Una sola aplicación web responsive (PWA) en React vs web en React + app móvil en React Native vs web en Angular + app nativa en Kotlin

**Contexto**:
- RES-08 exige que la plataforma pueda usarse desde computadoras y celulares, porque la mayoría de compradores y emprendedores usa el celular como canal principal. Hay dos públicos: compradores y vendedores (web) y personal interno (back-office). El sistema debe construirse y desplegarse en un ciclo con 5 integrantes (RES-10) y presupuesto limitado (RES-09). Según 0.1, el equipo conoce React (Almeyda, Gonzales, Luna, Santin) y Almeyda tiene experiencia en Android con Kotlin.

**Alternativas**:
1. **Una sola aplicación web responsive (PWA) en React con TypeScript, más el back-office en React**
   - Una base de código que se adapta a la pantalla del celular y se puede instalar en la pantalla de inicio; se despliega como archivos estáticos, sin pasar por tiendas de aplicaciones.
   - Menor acceso a capacidades nativas (p. ej. notificaciones push en iOS más limitadas).
2. **Web en React y app móvil en React Native**
   - Experiencia nativa en Android e iOS reutilizando React.
   - Un segundo proyecto que construir, probar y publicar en dos tiendas, con su propio ciclo de versiones.
3. **Web en Angular y app nativa en Kotlin**
   - Máximo rendimiento en Android.
   - Dos tecnologías nuevas para el equipo y sin app para iOS.

**Criterios de Elección**:
- Cumplir RES-08 (uso desde celulares) con el menor esfuerzo de construcción y operación.
- Conocimiento del equipo.
- Plazo del ciclo y cantidad de integrantes (RES-10).
- Coherencia con el lenguaje del backend (ADR-GLO-07).

**Decisión**:
- Se elige **una sola aplicación web responsive (PWA) en React con TypeScript** para compradores y vendedores, y **el back-office en React con TypeScript**. No se construye una app móvil nativa.

**Sustento**:
- Las funciones de Qhatu (buscar, comprar, seguir pedidos, publicar, gestionar ventas) no necesitan capacidades nativas del teléfono, así que una web responsive cumple RES-08 con una sola base de código. Cuatro de los cinco integrantes conocen React, y compartir TypeScript con el backend permite reutilizar los tipos de los contratos. Una app en React Native duplicaría el trabajo de construcción, pruebas y publicación en tiendas sin aportar a ningún escenario de calidad; queda como evolución si el negocio la necesita, ya que las APIs del backend son las mismas.

## Stack tecnológico consolidado

| Capa | Tecnología | Decisión |
|---|---|---|
| Nube | AWS, región sa-east-1, 2 zonas de disponibilidad | ADR-GLO-05 |
| Punto de entrada e identidad | Amazon API Gateway + Amazon Cognito (JWT) | ADR-GLO-02 |
| Cómputo | Amazon ECS sobre Fargate, Application Load Balancer interno | ADR-GLO-06 |
| Backend (todos los microservicios) | Node.js LTS + TypeScript + Express | ADR-GLO-07, ADR-VEN-06 |
| Base de datos relacional | PostgreSQL en Amazon RDS (una base por servicio) | ADR-GLO-04, ADR-VEN-04 |
| Mensajería entre módulos | RabbitMQ en Amazon MQ (outbox + consumidores idempotentes) | ADR-GLO-03, ADR-TAC-VEN-01 |
| Caché y almacén clave-valor | Redis en Amazon ElastiCache (un clúster compartido, prefijo de claves por módulo) | ADR-TAC-VEN-03 |
| Frontend (web responsive y back-office) | React + TypeScript, PWA responsive | ADR-GLO-08 |
