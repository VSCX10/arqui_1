# 0.2.1. Integrante 1 (ALMEYDA)

## 1. Desarrollo conceptual

### 1.1. ¿Qué son las bases de datos NoSQL de clave/valor?

Una base de datos de clave/valor organiza la información mediante identificadores únicos (**claves**) a los que se asocia un **valor**. En lugar de localizar datos mediante consultas con varias tablas y relaciones, una aplicación puede recuperar un valor a partir de su clave conocida. La estructura del valor depende del motor: puede tratarse de texto, números o colecciones especializadas.

Un ejemplo sencillo es la clave `carrito:usuario123`, que identifica el carrito de un comprador. En Redis podemos representarlo como un *hash* de pares campo–valor: `producto101 → 2` y `producto205 → 1`.

NoSQL agrupa distintos modelos de datos, entre ellos documento, grafos, columna ancha y clave/valor. Por tanto, **NoSQL no significa necesariamente que una base de datos no soporte SQL**, sino que existen modelos y mecanismos distintos del modelo relacional tradicional.

### 1.2. Problema y motivación

En aplicaciones con muchas consultas repetitivas, información temporal o sesiones activas, depender siempre de una base relacional puede aumentar la carga del sistema. Un carrito de compras es un ejemplo: un usuario puede agregar, quitar o modificar productos muchas veces antes de realizar una compra.

Una base de clave/valor permite mantener el estado del carrito identificado por usuario con operaciones sencillas, sin exigir una consulta relacional para cada interacción. Sin embargo, no reemplaza automáticamente una base de datos transaccional para operaciones como confirmar un pago o almacenar permanentemente un pedido.

### 1.3. Conceptos y componentes principales

- **Clave:** identificador único de un dato, por ejemplo `carrito:usuario123`.
- **Valor:** dato o estructura asociada a la clave. Redis admite, entre otros, cadenas, hashes, listas, conjuntos y conjuntos ordenados.
- **Hash:** estructura de campos y valores útil para representar cantidades de productos de un carrito.
- **TTL (Time To Live):** tiempo de vida de una clave; permite eliminar carritos abandonados cuando vence su plazo.
- **Cliente Redis:** biblioteca que usa la aplicación para enviar comandos al servidor Redis.
- **Persistencia:** posibilidad de escribir datos en disco mediante instantáneas RDB y/o registro AOF, con distintos compromisos de durabilidad.

### 1.4. Relación con la arquitectura de software

El modelo clave/valor favorece escenarios con acceso por identificador, operaciones frecuentes sobre información temporal y baja complejidad de consulta. Redis también ofrece expiración de claves, lo que resulta útil para sesiones y datos con vida limitada.

Desde la perspectiva arquitectónica, debe considerarse lo siguiente:

| Atributo | Contribución o riesgo |
|---|---|
| Rendimiento | Evita consultas relacionales para cada modificación del carrito; el resultado depende de red, configuración y carga. |
| Escalabilidad | Puede descargar trabajo de una base transaccional, aunque requiere dimensionar memoria y conexiones. |
| Disponibilidad | Agrega una dependencia operativa; una caída de Redis puede afectar el carrito si no existe una estrategia de recuperación. |
| Seguridad | Debe protegerse el acceso, configurar permisos y evitar la exposición del puerto de Redis a Internet. |
| Mantenibilidad | Simplifica operaciones sencillas por clave; puede complicar consultas complejas o relaciones entre entidades. |
| Consistencia y durabilidad | Su uso debe distinguir datos temporales de información que requiere transacciones o garantías fuertes de persistencia. |

En el proyecto Qhatu, la decisión **ADR-PED-03** propone Redis para almacenar los carritos y PostgreSQL para los pedidos confirmados. La investigación individual toma ese contexto como referencia, pero la demo será independiente de la implementación completa del proyecto.

## 2. Consideraciones técnicas

### 2.1. Tecnología escogida: Redis

Redis es un motor de datos en memoria que permite almacenar y consultar distintas estructuras, incluyendo hashes. Para la demostración utilizaremos **Node.js + Express** como API HTTP y **Redis** como almacén clave/valor. Esta elección facilita mostrar operaciones CRUD del carrito mediante peticiones HTTP.

### 2.2. Requisitos previos

- Docker Desktop con motor de contenedores Linux (en Windows), o Docker Engine en otro sistema.
- Node.js y npm instalados.
- Editor de código, por ejemplo Visual Studio Code.
- Una herramienta para realizar solicitudes HTTP, como Postman o `curl`.
- Puerto local `6379` disponible para Redis y un puerto de desarrollo para la API.

### 2.3. Instalación y puesta en marcha de Redis

**Paso 1.** Verificar que Docker funcione:

```bash
docker --version
```

<img width="810" height="272" alt="Captura de pantalla 2026-10-22 120949" src="https://github.com/user-attachments/assets/10438623-1c8a-422c-bb2f-ea542be87f6c" />

**Paso 2.** Levantar Redis en un contenedor local de desarrollo:

```bash
docker run -d --name redis-carrito -p 127.0.0.1:6379:6379 redis:7
```

El enlace a `127.0.0.1` limita la publicación del puerto al equipo local. La etiqueta `redis:7` es una opción de laboratorio; al desarrollar la aplicación se deberá registrar la versión efectivamente utilizada.

<img width="1292" height="300" alt="Captura de pantalla 2026-10-22 121418" src="https://github.com/user-attachments/assets/7fd01db0-51ac-4ae1-8a31-fdea4be61473" />

**Paso 3.** Comprobar que el servidor responda:

```bash
docker exec -it redis-carrito redis-cli PING
```

Resultado esperado: `PONG`.

<img width="1107" height="65" alt="Captura de pantalla 2026-10-22 122029" src="https://github.com/user-attachments/assets/8823b748-7b1f-4cd6-bfdd-d83797beb287" />

**Paso 4.** Probar manualmente un hash de ejemplo:

```bash
docker exec -it redis-carrito redis-cli HSET carrito:demo producto101 2
docker exec -it redis-carrito redis-cli HGETALL carrito:demo
docker exec -it redis-carrito redis-cli EXPIRE carrito:demo 1800
docker exec -it redis-carrito redis-cli TTL carrito:demo
```

Los comandos permiten crear el hash, consultar sus campos, establecer vencimiento de 30 minutos y leer el tiempo restante. La API final usará claves propias por usuario y no dependerá de `carrito:demo`.

<img width="1372" height="565" alt="Captura de pantalla 2026-10-22 122220" src="https://github.com/user-attachments/assets/27302c28-0796-4889-80b6-a9e8d5041c4d" />

**Paso 5.** Cuando se termine el laboratorio, detener el contenedor si ya no se necesita:

```bash
docker stop redis-carrito
```

**Nota técnica:** este contenedor sin volumen es apropiado para una práctica temporal, no para información crítica de producción. En producción se deben definir autenticación, red privada, monitoreo, respaldos y estrategia de persistencia.

### 2.4. Aplicabilidad

El modelo clave/valor suele ser conveniente para carritos, cachés, contadores, preferencias simples, estados temporales y ciertas sesiones. No resulta la primera opción para consultas con múltiples relaciones, reportes analíticos complejos o datos que deban conservar una integridad transaccional estricta entre varias entidades.

### 2.5. Beneficios y trade-offs

| Ventajas | Costos o limitaciones |
|---|---|
| Operaciones directas por clave | No resuelve de forma natural consultas relacionales complejas |
| Estructuras como hashes para agrupar campos | Requiere diseñar convenciones de nombres y expiración |
| TTL para información temporal | Se necesita una política frente a expiración o pérdida de datos |
| Puede descargar operaciones frecuentes de PostgreSQL | Añade otro servicio, configuración y monitoreo |
| Se puede combinar con una base relacional | Hay que definir la fuente de verdad para evitar inconsistencias |

### 2.6. Alternativas y criterio de selección

- **PostgreSQL:** apropiado si se necesitan relaciones, transacciones y consultas complejas; también puede guardar carritos, pero concentra más operaciones en la base relacional.
- **Memcached:** alternativa ligera para caché de clave/valor; tiene un conjunto de estructuras y capacidades diferente del de Redis.
- **Almacenamiento local del navegador:** sencillo para un carrito anónimo, pero no sincroniza por sí solo dispositivos ni proporciona un estado controlado en servidor.

Se selecciona Redis para esta demostración porque permite representar un carrito mediante hashes, aplicar TTL y visualizar operaciones de lectura y escritura desde una API. Es una **elección de diseño del ejercicio**, no una comparación experimental de rendimiento.

## 3. Propuesta de demostración funcional

### 3.1. Escenario

Se desarrollará una pequeña API de **carrito de compras** que permita identificar el carrito por usuario y mantener las cantidades de productos en Redis. La aplicación no procesará pagos, no validará existencias reales y no integrará proveedores externos: su propósito es demostrar el funcionamiento de un almacén clave/valor.

| Funcionalidad | Operación prevista | Evidencia |
|---|---|---|
| Agregar un producto | Crear/actualizar un campo dentro de un hash Redis | Respuesta HTTP y consulta a Redis |

## 4. Relación con el proyecto grupal Qhatu

El módulo Carrito, Pedidos y Notificaciones de Qhatu distingue operaciones temporales del carrito y operaciones persistentes de pedidos. En la documentación grupal, el **ADR-PED-03** propone usar Redis con claves `ped:carrito:{compradorId}` y expiración de 30 días; mientras que el **ADR-PED-04** establece PostgreSQL para pedidos, subpedidos y transiciones de estado.

La demo del informe individual se limita a ilustrar la primera parte: leer y escribir un carrito en Redis. No implementa el checkout real de Qhatu, ni constituye una prueba del rendimiento objetivo del módulo. Su ventaja es permitir comprender cómo podría utilizarse la base de datos elegida para una función concreta del marketplace.

## 5. Conclusiones

Las bases de datos NoSQL de clave/valor ofrecen una forma directa de almacenar y recuperar datos identificados por una clave. Redis resulta especialmente ilustrativo para carritos de compra, porque permite utilizar hashes y establecer expiración a nivel de clave.

Su adopción requiere decidir qué información puede ser temporal y cuál debe mantenerse de manera transaccional. Para Qhatu, Redis es una propuesta razonable para el carrito, mientras que el historial y la confirmación de pedidos requieren un modelo de persistencia distinto, tal como refleja la documentación de arquitectura del grupo.

La demostración y sus pruebas permitirán verificar el uso de Redis a nivel funcional. Hasta ejecutar el código, **no se pueden afirmar resultados de tiempos de respuesta, disponibilidad ni cumplimiento de metas de carga**.
